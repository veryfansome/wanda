# Multi-account mail and memory provenance

Status: draft, revised after two review rounds and five owner decisions (see the Review log). Nothing here is implemented. Rounds of review append to the "Review log" at the end; decisions change only by editing the numbered decision they replace.

## 1. Goal

wanda remembers things. Most of what it knows has nothing to do with anybody's mail: how the recycling collection works, what a topic it has been asked about involves, what it concluded in a conversation last week. Memory is general, and a memory is recorded and recalled on its own merits.

Some memories are user-related, and that is where ownership applies. A memory can come from a mailbox, in which case it belongs to that mailbox's account and its owners. It can come from a person in a conversation, in which case it belongs to whoever said it and whoever was there to hear it. It can come from both, or from neither.

wanda manages several mailboxes (iCloud now, Gmail later), each with its own owners: the Slack users whose word governs that account's mail. One shared vault holds everything; wanda recalls all of it and decides in each response what the readers of that conversation should be told. The harness's job is to make that decision well informed: every memory carries where it came from, every session is told who can read the conversation and which accounts each reader owns, and the tools a session already has answer the same questions on demand.

The harness stays authoritative where there is no model in the loop or where it already is today: which account a rule governs, whose confirmation makes a rule the owner's word, and where harness-posted digests, proposals and alerts go. Owners never type commands: they say what they want in plain language, a session turns it into a proposal wanda posts, and a reaction on that proposal is the owner's word.

Non-goals for this plan: more than one Slack workspace (one bot token, one socket), OAuth for Gmail (app passwords first), a rule engine for content-based triage policy, any change to the classifier's per-email judgment, harness-enforced filtering of what a session may recall, a restricted session mode, and any compatibility with databases, vaults or env files written before this change. There is no deployment and nothing to migrate (`docs/todos.md:7-9`); schemas, grammars and config change in place.

## 2. Vocabulary

- **Account.** A mailbox: name, provider, address, auth, Trash folder, triage channel, owners, enforcement, allowlist, caps. Configured only in `accounts.toml` (D1).
- **Owner of an account.** A Slack user id listed in that account's `owners`. "Owner" alone means owner of at least one account. Every account has at least one owner.
- **Audience.** The set of Slack user ids who can read a conversation, computed by the harness and stated to the model (D4). Never contains wanda's own user id.
- **Provenance.** Where a memory came from, stamped by the harness and shown to the model (D5). A memory may carry **account provenance** (the accounts whose mail it derives from), **conversation provenance** (who said it and who was present), both, or neither.
- **General memory.** A memory with no provenance markers: not derived from anyone's mail, not something a person told wanda in a conversation. It is unrestricted; anyone may hear it. This is the ordinary case for facts about the world.
- **Trust statement.** The block every seed carries: the readers of this conversation, the accounts each owns, and how to use the provenance markers (D7).

## 3. Decisions

Each decision names the alternatives considered. Reviewers should attack the decision, not the alternatives.

### D1. Accounts live in a TOML file, the only source of account configuration; secrets stay in `.env`

`accounts.toml` at the package-anchored path beside `.env` (`wanda/config.py:22`; the plist's WorkingDirectory is the repo root), overridable with `WANDA_ACCOUNTS_FILE`. Parsed with the stdlib `tomllib` into a pydantic `Account` model; no new settings source.

```toml
[[account]]
name = "home"                    # [a-z0-9][a-z0-9-]{0,31}; appears in ledger acct fields
provider = "icloud"              # icloud | gmail
address = "you@icloud.com"
password_env = "WANDA_ACCOUNT_HOME_PASSWORD"
owners = ["U0123", "U0456"]
triage_channel = "C0AAA"         # unique across accounts (validated)
enforcement = "shadow"           # shadow | live
never_trash = ["icloud.com", "apple.com"]
trash_confidence_min = 0.8
trash_cap_hourly = 5
trash_cap_daily = 20
trash_folder = ""                # empty = SPECIAL-USE discovery, then provider default
```

Per-account: everything above plus `imap_host`, `imap_port`, `idle_timeout_s`, `poll_fallback_s`, `snippet_bytes` (provider defaults). Global on `Config`: Slack tokens, `slack_allowed_user_ids`, claude binary and models, `email_triage_batch_size`, `email_triage_debounce_s`, `email_triage_timeout_s`, `email_triage_max_budget_usd`, `email_dryrun_max_limit`, `daily_run_cap`, memory settings, data dir.

The account-bound fields leave `Config`: `email_icloud_email`, `email_icloud_app_password`, `email_imap_host`, `email_imap_port`, `email_trash_folder`, `email_idle_timeout_s`, `email_poll_fallback_s`, `email_snippet_bytes`, `email_enforcement`, `email_never_trash`, `email_trash_confidence_min`, `email_trash_cap_hourly`, `email_trash_cap_daily`, `email_triage_slack_channel_id`, `memory_owner_user_ids`. Their env names, and the bare pre-rename names already in `LEGACY_ENV_NAMES`, are refused at startup with one message pointing at `accounts.toml`. A single account is one `[[account]]` block; there is no env-only path.

Validation: names unique and grammar-checked, owners non-empty for every account, provider known, triage channels unique, at most 8 accounts, at least one account.

Secrets: `Config.account_password(name)` resolves `password_env` from `os.environ`, then from the same env files `Config.model_config["env_file"]` names, via `dotenv_values`, the lookup `legacy_env_names_in_use` already performs (`wanda/config.py:205-214`). Nothing exports `.env` into the process environment, so a bare `os.environ` lookup would find nothing under the documented deployment. A missing secret is refused at startup by the per-account settings check, naming the variable; it is never discovered at IMAP login.

The TOML parse runs when `Config.accounts` is first accessed, not in `load_config`; the `hook` subcommand is dispatched before `load_config` and reads only `WANDA_DATA_DIR`, and the `slack` and `memory` verbs never touch accounts, so a half-edited file cannot break in-flight sessions' audit hooks or `wanda slack post`.

`wanda accounts` (new CLI verb, usable by sessions) prints each account's name, provider, address and owners. It is the session's way to answer "who owns what".

Alternatives rejected: nested env vars (`WANDA_EMAIL_ACCOUNTS__HOME__ADDRESS`) are unreadable at five accounts; a pydantic-settings TOML source adds a dependency for nothing tomllib does not do; keeping the flat env as a second way to define one account would be two sources of truth for an allowlist, the failure the legacy guard exists to prevent.

### D2. Tests configure accounts through one helper

The fifteen fixtures that construct `Config(_env_file=None, email_enforcement=..., memory_owner_user_ids=[...])` move to a conftest helper `accounts_cfg(*Account, **global_overrides)` that builds a `Config` with an in-memory accounts list (no file). `Account` is constructible directly in tests with defaults for everything but `name`, `address`, `owners` and `triage_channel`. `tests/test_config.py` asserts: bare and `WANDA_EMAIL_*` account names are refused with the pointer message, a file with a missing `owners`, an unknown `provider`, a duplicate channel or zero accounts is refused, and the global `email_*` settings still load from env.

### D3. Account identity is a column on every row that has one, and the dedupe key is account-qualified

- `messages.account TEXT NOT NULL`; `dedupe_key` is `f"{account}:{message_id or folder:uidvalidity:uid}"` (`wanda/watchers/imap_watcher.py:158-159`, `wanda/main.py:1271`). The same Message-ID delivered to two mailboxes is two rows, two triage runs, two moves. Mailboxes are independent and their owners differ; deduping across them would trash in one and not the other (`wanda/store.py:322-328`).
- The triage memo cause is `f"m:{account}:{sha_text(dedupe_key)[:12]}"` (`wanda/memory/service.py:292`). Today's `m:{key[:12]}` would be almost all prefix once the key carries an account name.
- `imap_cursor` primary key is `(account, folder)`, written directly into `SCHEMA`. No rebuild, no `user_version`, no `MIGRATIONS` entry: there is no database to migrate. The hand-built legacy fixture in `tests/test_processor.py:427-451` is updated to the new shape since it tests earlier backfills, not this change.
- `tasks.account TEXT NULL`: set for email tasks from the message; NULL for mention, guest and DM tasks. `tasks.audience_json TEXT NULL` (D4). `create_task` gains keyword-only `account` and `audience` so the twenty positional call sites in tests stay valid.
- `memory_run_windows` gains `account TEXT NULL` (the conversation's anchor account, when it has one: an email task takes the message's account, and a task whose channel is an account's triage channel or digest thread takes that account), `asker TEXT NULL` and `audience_json TEXT NULL`. These are what the CLI stamps as a line's provenance (D5). Any of them may be absent, and a line written in a conversation with none of them is simply general; no conversation is unrecordable. `open_run_window` gains keyword-only `account`, `asker` and `audience`. The row is a cache of the daemon's in-memory `Authority.windows`, as `kind` is today (`wanda/memory/service.py:103-107`).
- `memory_owner_checks` gains `author TEXT` and `accounts_json TEXT`, written as a cache and repaired from daemon memory like `verified` (`wanda/memory/passes.py:541-544`); no tier decision reads them (D6).
- `memory_proposals` (D6) replaces `memory_offers`: id, kind, accounts, text, ref, source (`slack:<channel>:<ts>` of the owner's message; NULL for a nightly offer), proposal (`slack:<channel>:<ts>` of wanda's posted message; NULL until posted), proposed_by (task id or `nightly`), created, confirmed_at, confirmed_by, ulid, declined_at, expired_at, revoked_at. Rows are never deleted, so a declined or expired proposal is not re-offered next night. `memory_digest` gains `channel TEXT NOT NULL`: one row per destination channel, so a line that belongs in two channels is two rows and one channel's failure never re-posts or blocks the other (Step 2).
- `digests.local_date` key is `f"{account}:{date}"` for triage digests and `f"memory:{account}:{date}"` for memory digests (the memory digest already namespaces, `wanda/memory/digest.py:24-25`). `meta` keys `last_successful_poll_at` and `imap_mode` are suffixed `:{account}`.
- Alert meta keys are `{kind}:{channel}_alert_pending` and `_date`. `cap` alerts go to their account's channel; `breaker`, abandoned, `memory_hourly` and `memory_nightly` fan out to every account's channel, each `(kind, channel)` pair tracked separately, because a post can fail on one channel after succeeding on another and one key per kind would re-post to the channels that already succeeded. The drain flushes every pair.
- Trash caps count per account (`trash_count_since(since, account)`, `wanda/store.py:433-438`). The daily run cap stays global: it bounds one subscription.
- `sender_stats` and `senders_since` take an account (`wanda/store.py:693-736`). Offers are computed per account.
- `meta` carries `accounts_running`: name, provider, address, host, port, triage channel and owners per account, plus the accounts file's sha, written at startup and after every successful rebind. `wanda doctor` is a separate process with no view of the daemon's memory, so this is what it compares the file against.

### D4. Audience is current membership, computed by the harness and stated to the model

- Sources: `im` is `{asker}`. Group DMs and private channels are `conversations.members`, paged, fetched fresh before every turn through the paced `_call` in `SlackActions` (the manifest already grants `channels:read`, `groups:read`, `im:read`, `mpim:read`), under the per-task lock, in `Processor._handle_slack`, never on the socket-mode thread. One paged call per turn is negligible against a run bounded by `agent_timeout_s`.
- wanda's own user id is subtracted. `SlackActions` learns it lazily from `auth.test` through `_call` on first use. Other bot users are listed as readers with a "(bot)" mark, since an integration in the channel can read it.
- A reader is rendered as `@<display name> (U0123)`, and every ownership clause is keyed by the id, computed for non-owners too (`owns: no account`). Display names are self-set and not unique, so the name is folded (`( ) : , [ ] @ < >` replaced) and sanitized wherever it reaches prompt text, including the asker line and the classifier's reader list, and `transcript.render` appends the id to any speaker whose name is shared. Names and `is_bot` come from the user cache with a one-hour TTL; on a first turn at most 30 uncached readers are resolved and the rest are listed by id.
- For the classifier, `members(triage_channel)` is fetched per batch; on failure the audience line reads `read by: unknown`. A failed per-turn refresh stores `audience_json = {"unknown": true, "at": …}`, so the seed, the resumed turn and the CLI hint say the readers could not be determined rather than showing a stale list as current.
- A public channel (`conversations.info.is_private` false) is stated as public: "anyone in the workspace can read this channel", with the joined members listed. The model treats a public channel as readable by everyone. `users.list` is not fetched.
- `members(channel)` that fails or truncates (the `slack_cli.py:159-177` pattern stops silently after ten pages) yields an "unknown readers" statement, never a partial list presented as complete.
- Email task: the audience is the members of the account's triage channel. When it contains a non-owner of the account, or the channel is public, the daemon posts a once-a-day `audience:{account}` alert in that channel naming the ids, and doctor repeats the check. The session is still run and told.
- `audience_json` is stored on the task at the first turn and refreshed before every turn; it is what the trust statement is built from. Nothing is gated on it: resume, replay of prior DM answers, and delivery work as today.
- Reactions: the manifest gains the `reactions:read` scope and the `reaction_added` and `reaction_removed` bot events (neither exists today, `slack/manifest.yaml:33-58`; the app is re-installed once). The bot token never carries `reactions:write` and the optional user token keeps read scopes only. That is load-bearing: a reaction by an owner's id is the owner's word, so the daemon must hold no credential able to produce one. Doctor calls `auth.test` with each token and fails on any write scope granted to the user token.
- The watcher, which drops every non-`message` event today (`wanda/watchers/slack_watcher.py:88`), gains one branch: a reaction whose `item.type` is `message` and whose `(item.channel, item.ts)` matches a proposal row is enqueued as an `Event(kind="reaction")` and handled in the processor; every other reaction is ignored. Its dedupe key is the envelope `event_id`, not the message key `f"{channel}:{ts}"` (`:143`), which would collapse a later 👎 onto an earlier 👍.
- Reaction names are compared after stripping a `::skin-tone-N` suffix; `+1` and `thumbsup` confirm, `-1` and `thumbsdown` decline. `reactions.get` is always called with `full=True`, since the default response can truncate the `users` list.
- Socket Mode can drop events during reconnects, so events are only a fast path: the hourly pass re-fetches with `reactions.get` and is the source of truth.
- Alternatives rejected: gating resume and replay on audience change, harness-side visibility filtering, and a restricted no-Bash mode, all of which round 1 designed and the owner declined; they moved disclosure out of the model's hands, which is the opposite of the goal.

### D5. Provenance: stamped by the harness, optional, shown to the model, never merged across accounts

A memory records where it came from. There are two independent markers and a memory may carry either, both or neither; a memory with neither is general and unrestricted.

- **Ledger fields.** `acct=` (sorted, comma-joined account names), `by=` (one Slack user id), `heard=` (the ids present when it was said, including the speaker, or the sentinel `public`). All three join `_FIELD_KEYS` (`wanda/memory/ledger.py:28`), all three are optional, and `parse_line` validates each: account names against the D1 grammar, ids against `^[UW][A-Z0-9]{2,}$`. `by` and `heard` appear together or not at all. The dead `tier` key is removed in the same change. A line with none of them is general, which is the ordinary shape for a fact about the world and keeps today's fixtures valid with no edit.
- **Who stamps what, from what the harness knows.**
  - A triage memo takes `acct=` the row's account and no speaker: mail is not a conversation (`wanda/memory/service.py:292`).
  - A line a session writes with `wanda memory note|open` takes `by=` the asker and `heard=` the task's audience, from the task row, plus `acct=` the conversation's anchor account when it has one (an email task thread, an account's triage channel or its digest thread). Both come from the run window, never from the session's arguments or environment; `WANDA_SLACK_USER` is set into every session today and read nowhere, and stays informational.
  - A session may declare a line general with `wanda memory note --general` when the fact did not come from the person it was talking to: a web search result, a conclusion of its own, a public fact. The harness still stamps the conversation it was written in, so the rendered marker reads "recorded as general, in a conversation with @robin"; nothing is hidden, and the model's classification is visible rather than silent. This is the model deciding, which is the stance, and the alternative (the harness guessing) would file every web fact as the owner's private word.
  - An owner line minted from a confirmed proposal takes `acct=` the account the proposal names and `by=` the confirming user; `heard=` is the proposal message's channel audience.
  - A claim the passes mint takes the union of its witnesses' markers.
  - A hand-typed claim takes the note's frontmatter when it has one, else the markers of the run window covering the file's mtime, else none.
- **Nothing is unrecordable.** There is no conversation in which a session cannot write a memory. A DM with someone who owns no account, a group DM of owners with disjoint accounts and a public channel all record: the line simply carries conversation provenance and no account, or nothing at all. The refusal an earlier draft specified is gone with the requirement that produced it.
- **Fingerprint.** `line_fingerprint` covers `acct`, `by` and `heard` (`wanda/memory/ledger.py:133-137`), so a held owner line whose markers are rewritten on disk loses authority.
- **Claims.** `acct::`, `said-by::` and `heard-by::` join `EDGE_RELS`, and `acct::` joins `TRUST_RELS` since it gates mail authority; a new `Claim.values(rel)` returns every scalar, as `Claim.value` returns only the first. An unregistered rel is re-parsed as an owner-typed claim (`tests/test_memory_notes.py::test_an_unknown_rel_becomes_the_owners_plain_claim`), which is why all three are registered.
- **Index.** `acct`, `said_by`, `heard` on `obs` and `claims`; `acct` on `rules` and `docs`. A claim's markers are the union of its witnesses'; a declared edge never contributes when a witness exists and is flagged `provenance-mismatch` when it differs, mirroring `tier::` (`wanda/memory/index.py:500-502`). A claim with no witnesses takes the run window covering the file write, else the frontmatter, else none. `wanda memory show` renders from the index row, not the declared edge.
- **Merging never crosses accounts, and unions listeners.** The grouping keys gain `acct` only: `ix_obs_group (subject, facet, norm, acct)`, `_group_support` (`wanda/memory/index.py:525-538`), `graduation_candidates` (`wanda/memory/passes.py:1264-1299`), `l1_groups` (`wanda/memory/render.py:51-80`), `contradiction_candidates`, `_best_match` and direct support, `_merge_into` on retire, and `_apply_rule`'s supersede. Two accounts' observations about one sender stay two claims, because merging them would lose the provenance the model needs. Two people saying the same thing is corroboration, not a conflict, so speakers and listeners are unioned into the claim and raise its support as a second witness always has. General observations merge with each other freely.
- **The rules key is `(acct, facet, target)`,** with exactly one account since a `rule` proposal names one (D6); `dispositions_for(..., account)` matches on it and `_apply_rule` supersedes only a predecessor with the same target and account (`wanda/memory/index.py:575-582, :649-657`).
- **Vetoes** are keyed per account when the forget line carries one (`{acct}:key:{subject}|{facet}`) and globally when it does not, recomputed identically by `forget_observations` and the verifier (`wanda/memory/commands.py:292-305`). A `forget` about one mailbox must not blind another's triage; a `forget` of a general fact applies everywhere, which is what it means.
- **Memo saturation and `cause_key`** count per `(subject, facet, acct)` (`wanda/memory/service.py:307-312`, `wanda/memory/index.py:126-131`).
- **Rendering.** One helper `tagged(tier, provenance, text)` renders every bracket and folds `[`→`(` and `]`→`)` in the text, title or address it wraps; `clean_text` folds single brackets at write time too (it already folds `[[`), so a memo, claim, note title or sender address containing `[rule · home]` cannot put a second tag on a line. A general memory renders as today, `[noted]`. An account memory renders `[noted · home]`. A conversation memory renders `[noted · from @robin, heard by @robin @sam]`, or `in private` when the speaker was alone with wanda, or `heard by the workspace` for `public`. Both markers render together when both apply. The sites: L1 lines and the export (`wanda/memory/render.py:106, :237`), the triage block's sender and rule lines (`wanda/memory/recall.py:256, :289`), `for_agent` and `walk` (`:118, :195`), the projection's standing rules and roster (`wanda/memory/render.py:332-357`), and every `memory_cli` read verb (`:154, :185, :198`). The grammar is taught in the five places that describe tags to a model: `MEMORY_NOTE`, the export README, `header_text`, `prompts/email_triage.md`'s Memory section, and the wanda-memory skill.
- **Write-spec rewrites** (`wanda/memory/passes.py:1704-1720`) use preference claims of every provenance; the guides are filing rules, not facts.
- Alternatives rejected: requiring an account on every line, which was the previous draft and forced a fact about the recycling schedule into a mailbox and made whole conversations unrecordable; a single "scope" field spanning accounts and people, which conflates a mailbox with a person and cannot express "Robin said this in a room with Sam"; letting the harness infer generality, which would file every web search result as the owner's private word.

### D6. An owner's word is a reaction on a proposal wanda posted; the account comes from the conversation; nothing minted trusts wanda.db

- **No command grammar.** The Slack-facing `rule`, `attest`, `pin` and `forget` commands are retired, with `commands.parse_command`, `is_command`, `commands.handle`, `expected_for_message` and the watcher's `command` kind (`wanda/memory/commands.py:40-107, 208-365`; `wanda/watchers/slack_watcher.py:112-117`). An owner's message is a message: it opens or resumes a session like any other, and the session reads it. Cost accepted: a rule now costs one session run where a typed command cost none.
- **Proposals.** A session that reads a standing instruction in the owner's words runs `wanda memory propose --kind rule|pref|attest|pin|forget [--account <name>] ...` with structured arguments. The CLI builds the text from the same closed templates the commands used (`rule_text` and the attest/pin/forget texts, `wanda/memory/commands.py:137-143`), posts it as a plain-text message in the conversation the session was triggered from, with `unfurl_links=False`, no blocks and no attachments, and records a `memory_proposals` row (D3). The posted text reads: "Proposed for home: trash mail from newsletter.example (from your message ‹link›). React 👍 to confirm, 👎 to drop. Removing your 👍 later withdraws it." The model supplies arguments, never prose, so an owner rule still never carries model text.
- **The anchor.** `anchor(channel, thread_ts)` is one function: an email task thread resolves through the task's message to its account; a channel that is an account's `triage_channel` (which covers its task threads and its digest threads, both posted there) resolves to that account; anything else is unanchored. It reads only Slack's own channel and thread values and the accounts snapshot, never `tasks`, `messages` or `digests` rows, which a session can rewrite. A `rule` proposal names exactly one account. In an anchored conversation the named account must equal the anchor's, or nothing mints and nothing verifies; only an unanchored conversation may name another account, or several for a `pref`, `attest`, `pin` or `forget`. `wanda memory propose` refuses a mismatch too, but that refusal is a convenience: the check that matters runs at confirmation and at every verification.
- **Nothing minted reads wanda.db.** On a qualifying reaction, and again in the hourly scan of pending proposals, the harness fetches the message at `(channel, ts)` and mints only from what it fetched: the message must be authored by wanda's bot user, carry no `edited` field, no `blocks`, `attachments`, `files` or `subtype`, and its text must `fullmatch` the closed template, yielding the kind, the accounts, the text and any ref. The `memory_proposals` row supplies the `(channel, ts)` to fetch and the id to stamp, nothing else; a row whose kind, accounts or text disagree with the parse mints nothing and is named in the digest. This is the same stance today's code takes toward an offer row (`wanda/memory/commands.py:229-255`), extended to the whole mint.
- **Confirmation.** A proposal is confirmed when its message carries a confirming reaction by a user who currently owns every account it names, and no declining reaction by such a user; the earliest qualifying confirmation is the author of record. Both paths mint through `proposals.confirm()`, which takes the memory lock, claims the row with `UPDATE memory_proposals SET confirmed_at=?, confirmed_by=?, ulid=? WHERE id=? AND confirmed_at IS NULL AND declined_at IS NULL AND created >= now-7d`, and appends the ledger line, inserts into `Authority.minted` and stamps the check only when that update changed a row. A confirmed row whose ulid is absent from the ledger (a crash between the update and the append) is re-minted by the hourly scan. A decline records `declined_at`; expiry after 7 days records `expired_at`; neither deletes the row, so a declined or ignored offer is not re-offered. wanda replies in the proposal's thread on confirmation, decline, expiry, revocation and demotion, so every outcome is visible where the owner acted.
- **Revocation.** Removing the confirming reaction withdraws the word. A `reaction_removed` matching a confirmed proposal pops every ulid it minted from `Authority.minted` and `Authority.verified`, clears the check stamp, and the next rebuild demotes; the handler first re-runs `reactions.get`, so another qualifying owner's standing 👍 keeps the line alive with that user as the new author of record. A declining reaction added after confirmation revokes the same way. Without the event, revocation is bounded by the daily recheck (below), and the README says so.
- **Cadence.** `Authority.minted` and `Authority.verified` map ulid → (fingerprint, confirming user, checked_at) and are treated alike: the unconditional skip for minted lines (`wanda/memory/passes.py:550-551`) goes, and both are re-fetched when their in-memory `checked_at` is stale. The cadence is judged from that in-memory stamp, never from the `checked:` row in wanda.db, which a session can keep fresh. A minted line joins the daily cadence after its first pass.
- **Verification.** For each owner line the hourly pass fetches the proposal message named by the cause and re-derives everything from it: bot author, no `edited`, no blocks, template parse, anchor, and `reactions.get(full=True)` showing a qualifying confirmation. Anything else takes the plain pending path (`wanda/memory/passes.py:600-609`): tier drops, the rule leaves the table, a digest line names it, and a later pass that finds the reaction again restores it. A message carrying `edited`, or missing entirely, is tampering rather than a mismatch: wanda never edits or deletes a proposal, and only the bot token can, so the digest line says so and doctor counts these. The re-mint path is deleted with the grammar (`_resolve_mismatches`'s remint branch, `_remint_owner_edit`, `verify.remint`, `Authority.reminted`, the `reminted:` marks): a proposal's author is never the owner, so there is no "the owner edited their command" case left.
- **Authority is memory, wanda.db is cache.** `TrustOracle` becomes `line_checked(ulid, fp, acct)`, `line_authored`, `window_tier`; `owner_verified` leaves `tier_for_obs` entirely (`wanda/memory/index.py:91`). Today it reads `memory_owner_checks.verified` on every rebuild, so a session could flip that row, delete `memory.idx` to force an inline rebuild, and silently demote an owner rule for up to an hour; a held `(ulid, fingerprint)` already implies the row was written from that state, so the read buys nothing. The quarantine marks that skip verification (`wanda/memory/passes.py:530, 532`) move into `Authority` for the run and become a wanda.db cache too. `memory_owner_checks.author` and `accounts_json` are status and doctor cache only. So a session that edits wanda.db can neither demote nor resurrect a line.
- **One judgement.** `MemoryService._verifier()` is built whenever Slack is configured, no longer gated on an owner list, and receives the accounts snapshot. It never consults an owner list itself: ownership is judged only in `line_checked` at rebuild. Removing an owner from the file demotes their confirmed lines within the hour with zero Slack calls; re-adding restores them.
- **Priming after a restart.** `Authority` starts empty and the first hourly pass can be up to an hour away, so `adopt_shared_state` runs `_verify_owner_lines` under the memory lock before the daemon serves a seed, a triage block or a reaction. Until that pass completes, `apply_now` applies a new line's op but skips the rebuild, and the confirmation reply says the rule is live at the next pass. Without this, one reaction-triggered rebuild after a restart would demote every previously confirmed line and post a false demotion digest line for each.
- **Digest offers are proposals.** The nightly writes one `memory_proposals` row per offer (`kind=rule`, the account, the template text, `proposed_by=nightly`, `proposal` NULL) and no digest line. After the nightly, the digest poster posts one message per unposted row in that account's `memory:{account}:{date}` thread and records its `(channel, ts)`; it first scans the parent's replies for the proposal marker, the way `find_task_post` does, so a crash between posting and recording re-attaches instead of duplicating. Offer messages are their own messages, not lines inside the batched digest post, because a reaction targets a message. `make_offers` skips an `(account, text)` that has any proposal row or a live rule, which replaces `find_offer`. `memory_offers`, `rule kN` and the bare `kN` form go away.
- **No provenance trade-off remains.** The accounts are in the proposal text, the proposal message is what the verifier re-fetches, and an edited message is refused, so a line whose `acct=` or text is rewritten on disk loses authority while held and never re-verifies afterwards. The explicit account token that round 1 deferred is no longer needed.
- **Re-examination.** The claim a confirmed proposal graduates into carries `owner-said::` to the ledger line as today and a new informational `source::` edge (in `EDGE_RELS`, not `TRUST_RELS`) holding the owner's original message reference. `wanda memory rules` prints both links; a session asked why a rule exists can `wanda slack thread` around the source.
- **Effect of demotion.** The derived rule leaves the `rules` table; the prefs claim gets status `unconfirmed`, excluded from `LIVE_SQL`, and a digest line names it and links the proposal so the owner can react again. The superseded predecessor is not unfolded automatically. Alternative rejected: retiring the claim, which is irreversible and loses the record of what was said.
- **Owners are implicitly allowed to talk** to wanda regardless of `slack_allowed_user_ids`. `_is_owner` survives only for that.
- **Accounts snapshot.** `cfg.accounts` is an immutable object rebound atomically and never mutated, at startup, at the top of each hourly pass under the memory lock, and when a reaction is handled. Every unit of work reads it once into a local and passes it down; `StoreTrust` receives it in its constructor and `rebuild` takes it as a parameter. The socket thread reads the same attribute; a rebind is one assignment under the GIL.
- **What a re-read may change.** The file is session-writable, so an owner *addition* is honoured only at a restart, the barrier the plan already uses for account changes; *removals* take effect at the hourly re-read, the fail-closed direction. The bot's own user id is refused in `owners` and ignored as a confirming user whatever the file says. The owner-set hash is held in daemon memory from startup, and a change posts an immediate alert, not a digest row a session could pre-empt. The re-read replaces the snapshot only when the file parses and its account names and connection fields equal the running set; otherwise the last good snapshot stays in force with an immediate `_alert_once("accounts")`. Adding, removing or renaming an account requires a restart. Rows in `messages` whose account is not in the running set are skipped by every fetch and counted by doctor. The accounts file joins README's list of session-writable residuals; doctor prints its path, owner and mode.
- Alternatives rejected: binding a DM to every account the author owns (the owner declined it: the account must come from the conversation); auto-applying the model's interpretation with a digest link and revoke-after (no deterministic verification, and an injected session could mint a live trash rule); keeping the typed grammar as a fallback (two paths to the owner's word).

## 8. Review protocol

Each round runs independent reviewers with distinct lenses over this document and the code, verifies every finding against the code, and appends a dated entry below with: the finding, the decision it targets, the verdict, and the edit made. Lenses that have to be covered at least once: information the model is given (does every prompt carry a correct audience, ownership map and tags; can a tag be forged or missing), provenance and forgery (can a session mint or re-target authority over mail), defaults (does any absent value widen), Slack semantics (audience correctness across im, mpim, private and public channels, membership drift), concurrency (two watchers, two sessions, one store), operational (doctor, digest, alerts, restart), and testability (does every invariant have a test that would fail today).

### Owner decision 5, 2026-09-04: memory is general; ownership applies to user-related memories

The plan had one dimension, the account, and required it on every line, which made it email-centric in a way the owner did not intend. wanda should record and recall any fact, including ones about nobody; ownership is a property of the memories that involve people and their mail, not of memory itself.

D5 is rewritten from "scope is a required field" to "provenance is optional and has two independent markers": `acct=` for the accounts whose mail a memory derives from, and `by=`/`heard=` for who said it and who was present. A memory may carry either, both or neither, and one with neither is general and unrestricted, which is the ordinary case. Three consequences the previous draft got wrong are fixed: a fact Robin stated in a DM is no longer tagged as deriving from two mailboxes, which had also hidden it from a co-owner; a conversation whose readers share no account is recordable again, where the previous draft refused every write; and the speaker is recorded at all, where before only `src=agent` and the task id were, so two people in a group DM produced indistinguishable lines. A session may declare a fact general with `--general` when it came from a web search or its own reasoning rather than from the person, and the harness still renders the conversation it was written in, so the classification is visible rather than silent.

Merging follows the same split: it never crosses accounts, since that would lose provenance the model needs, but it unions speakers and listeners, since two people saying the same thing is corroboration. General observations merge freely.
